# Product Principles

Recurring discipline for every product-management skill in this collection (brainstorm, spec,
research market/tech-selection modes, oss-strategy). Each skill links this file rather than repeating
these rules. Apply them at all times — they sit alongside engineering-principles.md, not instead of it.

## 1. Need ≠ feature
"I want an upload button" is a feature; the need is "share files conveniently." Dig to the job the
user is trying to complete, not the feature they ask for. Features are solutions; needs are problems.
Never implement a requested feature without naming the underlying need it serves.

## 2. Behavior is data, statements are emotion
When what users do conflicts with what they say, trust the behavior. Ask about past behavior
(concrete, recent, specific), not future opinions ("would you use this?"). Stated intent predicts
nothing; actions and existing workarounds predict everything. This is the Mom Test.

## 3. Validate before building
The riskiest assumption — the one most likely to be wrong — gets validated first. The MVP's purpose
is to test that assumption, not to deliver a feature. If the first version doesn't feel embarrassing,
you waited too long. Code written before validation is code written on a guess.

## 4. Outcomes over outputs
Measure whether users truly received value, not how much you shipped. A North Star metric represents
user value realized; downloads, registrations, and feature counts are vanity metrics. "We shipped 12
features" is an output; "retention flattened at 40% by week 4" is an outcome.

## 5. Say no to good ideas
A product solves a specific pain for a specific someone — it is not everything for everyone. "A product
for everyone typically impresses no one." The Not-Doing list is mandatory and reasoned, not optional.
Good ideas that don't serve the chosen user and job are distractions; saying no to them is the core PM
skill, not a nicety.

## 6. Opportunity = demand × giant blind spot ÷ difficulty
General capability competes on capital (giants' battlefield — avoid). Industry vertical competes on
resources. Niche tools compete on execution — the individual developer's main ground. A reachable small
market beats a large but unreachable one. The market question is not "how big" but "can I reach and
serve these specific people."

## 7. Discovery precedes delivery
Problem-space discovery and solution-space delivery are two tracks running in parallel, not phases in
sequence. Continuously discover which problems are worth solving (opportunities) before committing to
solutions. Never hunt for a problem to fit a solution you've already built — that is building in the
delivery track with the discovery track switched off.

## 8. The real competitor is the current workaround
The user is already solving this problem somehow — spreadsheet, manual process, doing nothing. That
workaround is your real competitor, not the product that looks like yours. "Like X but better" is a
weak position when X isn't what users are actually doing today. Name the workaround; beat the workaround.
