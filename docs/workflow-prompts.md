# 开发流程提示词手册（文档先行）

> 一份面向 **engineering-skills** 33 个技能的「显式调用」提示词手册。按软件开发生命周期
> 9 个阶段（product → research → design → develop → tune → test → verify → ship → operate）
> 重新梳理，每个阶段给出：**用哪个技能 / 粘贴什么提示词 / 产出什么文档**。
>
> 核心理念：**文档先行，代码后行**。先写清楚要做什么，再动手写代码。

## 怎么用这份手册

1. 按阶段顺序往下走，每一步粘贴对应提示词到 Claude Code。
2. 提示词里 `/skill-name` 是显式调用；不确定用哪个技能时先 `/using-skills` 路由。
3. 规划用内置 plan 模式（`EnterPlanMode`/`ExitPlanMode`），不是某个技能。
4. 所有提示词默认遵循下方的【全局约定】，无需每次重复。

---

## 全局约定（适用于每一步）

这些规则贯穿全流程，是最高行为准则，不必在每个提示词里重复：

- **纯净原则（最高准则）**：一切代码和文档像第一次写出来的一样——抓根因不打补丁、代码自解释、不留残留文件、部署一致。敢于推倒重写。
- **文档先行**：先 spec / PRD，后代码；先 PLAN，后实现。
- **风格**：明确、简洁、成熟。尽量用 mermaid 图。不要版本号。不要"半成品"字样。
- **提问优先**：需求不明确时，**直接问我详细问题**，直到具备一致性和明确性再产出。
- **中文注释**：注释全部中文，重点解释功能；每个文件有文件头注释，每个关键函数有函数注释；尽量简洁。
- **测试**：测试代码写在 `test/` 目录下。**禁止 mock 测试**，必须真实调用、真实数据。
- **TODO**：代码有待完善处显式加 `TODO` 注释；已完成的 TODO 立即删除。
- **Git**：**绝不自动 `git push`**，所有推送必须人工确认，确保每次 push 的版本可运行。
- **不向后兼容**：尽量简洁，架构明确，不为兼容旧实现留过渡逻辑。
- **审计不输出报告**：`/documentation-audit` 只同步文档，不产审计报告，确保一致性和明确性即可。

---

## 文档结构（约定俗成）

仓库正式文档只保留以下 5 类（位于 `docs/`），其他合并或删除：

| 文档 | 职责 | 风格 |
|---|---|---|
| `docs/PRD.md` | 需求 | mermaid 为主，文字简洁 |
| `docs/TECH.md` | 架构 | mermaid 为主，文字简洁 |
| `docs/API/*.md` | API 契约 | 详细请求/响应 |
| `docs/FLOW/*.md` | 业务流程 | mermaid 流程 + 详细数据流描述 |
| `docs/TODO.md` | 不足与未来方向 | 按业务合并 |

根目录辅助文档：

| 文档 | 职责 |
|---|---|
| `ROADMAP.md` | 产品定位、多版本规划、每版本产品侧验收项 |
| `docs/PLAN.md` | 实现计划：说明要写的代码文件和对应单元测试，不含实际代码 |
| `docs/design.md` | UIUX 审计与优化建议 |
| `docs/FRONT.md` | 前端审计（目录/路由、组件划分、数据流、布局复用） |
| `CLAUDE.md` | AI 助手上下文指令（见下方生成提示词） |
| `README.md` | 使用方法、架构、功能、未来方向 |

> 调研类中间产物（`market.md`/`competitor.md`/`prdv2.md`）是 PRD 的输入，不进正式 5 类；上线前清理。

## 01 · product — 想清楚做什么

**技能**：`brainstorm`（仅用户显式调用）/ `spec` / `oss-strategy`

### 1.1 打磨想法

```
/brainstorm
我想做一个【一句话想法】。请一次问一个问题，盘问我，把模糊想法打磨成具体提案，直到可以写 spec。
```

### 1.2 产品路线图

```
输出 ROADMAP.md：产品定位、目标用户、主要功能、icon。
设置多个版本，每个版本列出产品侧的验收项。遵循纯净原则。
```

### 1.3 写 PRD（需求文档先行）

```
/spec
输出 docs/PRD.md，中文。直接问我详细的问题，直到需求具备一致性和明确性。
尽量使用 mermaid 图。不需要版本号。成熟风格，明确简洁。
```

### 1.4 开源策略（可选）

```
/oss-strategy
为这个项目制定开源策略：商业模式、open core / COSS、增长路径。
```

## 02 · research — 动手前先调研

**技能**：`market-research` / `tech-selection` / `research`

调研产物是 PRD 的输入，不是正式文档。流程：初稿 PRD → 调研 → 粗需求 v2 → 人+AI 审计 → 最终 PRD。

### 2.1 市场调研

```
/market-research
针对【产品方向】做市场调研：用户原话、竞品、行业情报。输出 docs/market.md（PRD 输入）。
```

### 2.2 技术选型 / 竞品对比

```
/tech-selection
针对【具体需求】对比可选技术栈/库/框架，输出对比矩阵 + 推荐。输出 docs/competitor.md（PRD 输入）。
```

### 2.3 深度调研（带引用）

```
/research
针对【主题】做深度调研，必须有来源引用，输出带引用的 Markdown（docs/prdv2.md，作为粗需求）。
```

### 2.4 审计并定稿 PRD

```
/spec
基于调研产物，完善不明确的需求，输出最终 docs/PRD.md。直接问我详细问题，直到一致且明确。
mermaid 为主，不需要版本号，成熟风格。
```

## 03 · design — 编码前先设计

**技能**：`architecture` / `domain-modeling` / `api-design` / `codebase-design` / `frontend-design` / `prototype`

### 3.1 架构设计

```
/architecture
输出 docs/TECH.md，中文。直接问我详细的问题，直到一致性和明确性。
尽量使用 mermaid 图。不需要版本号。成熟风格。包含 ADR 与架构图。
```

### 3.2 领域模型（复杂业务才用）

```
/domain-modeling
挑战术语、用场景压测领域模型，输出 CONTEXT.md（统一语言）+ 相关 ADR。
```

### 3.3 API 契约

```
/api-design
根据 PRD/TECH 设计 API 契约：REST/GraphQL、请求响应、版本、错误模型。输出 docs/API/*.md，详细请求/响应。
```

### 3.4 UIUX 审计与设计

```
/frontend-design
参考 Apple HIG 设计原则，深度审计当前前端布局/组件/字体/样式，给出优化建议。
输出 docs/design.md。需要在线样稿时配合 Figma，人工介入审计。
```

### 3.5 原型验证（设计问题用一次性原型回答）

```
/prototype
针对【设计问题】做一个一次性 HTML 原型（单一文件验证逻辑，或多套可切换 UI 对比）。
```

### 3.6 代码库深化（重构机会）

```
/codebase-design
审计代码库，找出深化模块/重构/可测试性机会，列出报告，逐个推进我选定的那个。
```

## 04 · develop — 实现

**技能**：`breakdown` / `context-engineering` / `implement` + `tdd`

### 4.1 拆解计划

```
/breakdown
输出 docs/PLAN.md，中文。直接问我详细的问题，直到一致性和明确性。
不需要包含实际代码，只说明要编写的代码文件和对应的单元测试代码。
第一版优先搭好模板职责和项目架构，不追求细节完成，追求整体系统结构。
```

### 4.2 审计文档一致性

```
/documentation-audit
审计并更新所有文档，确保与 PRD/TECH/PLAN 一致。明确简洁，不需要版本号，不需要审计报告。
```

### 4.3 生成 CLAUDE.md

```
/init
（或使用下方【CLAUDE.md 生成提示词】）
```

### 4.4 完善 .gitignore

```
请完善 .gitignore，添加需要忽略的文件，确保仓库简洁。不要完全覆盖现有配置，从文件末尾追加。
```

### 4.5 逐小步实现（TDD）

```
/tdd
@docs/PLAN.md 按计划逐文件实现。严格按照计划完成代码文件编写，测试代码写在 test/ 下。
有依赖要提前配置。代码有待完善处加 TODO 注释。禁止 mock 测试。
```

### 4.6 缺上下文时先打包

```
/context-engineering
为当前实现任务组装正确文件、定义和既有决策，打包进工作上下文。
```

## 05 · tune — 优化

**技能**：`performance` / `simplify` / `codebase-design`

### 5.1 性能优化（先量后优）

```
/performance
先 profile 找瓶颈，再针对性优化。输出 profile 结果 + 定点修复。禁止凭感觉优化。
```

### 5.2 简化代码

```
/simplify
@TODO.md 标识已完成项（打勾），修复待办，修复完移除相关 TODO 注释。
不要向后兼容，尽量简洁，架构明确。更新文档一致性。
```

### 5.3 深度重构架构

```
/codebase-design
深度审计后端架构，优化使架构完善，禁止硬编码。然后 /simplify 根据报告完全重构。
```

## 06 · test — 证明它能跑

**技能**：`tdd`（开发期）/ `test-generation` / `api-testing` / `e2e-testing`

### 6.1 生成测试

```
/test-generation
为【功能/文件】生成测试，覆盖用例矩阵。测试写在 test/ 下，禁止 mock，确保真实调用。
```

### 6.2 API 集成测试

```
/api-testing
分步骤，不要分支。本地运行后端。
根据所有 API 文档审计并完善后端集成测试，然后运行测试。
检查日志文件和后端 docker 日志以排查错误，不要阻塞太久。
将测试输出保存到临时文件，禁止 mock 测试。
优先检查测试代码，最后修改后端代码，测试完恢复原有状态。
```

### 6.3 前端 E2E + API 集成

```
/e2e-testing
/api-testing
完善所有前端 API 测试代码和业务 E2E 测试代码。
后端本地运行，前端直接发 API 请求验证响应。
检查日志和 docker 日志排查错误，禁止 mock。
优先检查测试代码，最后修改前端代码，测试完恢复原有状态。
```

### 6.4 验收测试

```
生成验收测试步骤，输出到根目录 test/ 目录，包含验收所需测试数据、用例和描述测试步骤的文档。
以数据库所有字段为参考，检查每个字段在后端是否有处理、有体现。禁止 mock，需要真实业务过程。
```

## 07 · verify — 合并前审查

**技能**：`code-review` / `debugging` / `security-review`

### 7.1 代码审查（每个大里程碑）

```
/code-review
深度检索前后端代码，每个代码文件都要查看到，给出优化建议。
待优化的地方加 TODO 注释，已完成的 TODO 删除。确保代码简洁、规范、严谨。
输出 docs/TODO.md（按业务合并，成熟风格，全量 TODO 注释一致性审计：代码 ↔ TODO.md 双向校验）。
```

### 7.2 修复 TODO

```
/simplify
@TODO.md 标识已完成项，修复 todo，修复完移除相关 TODO 注释。
不要向后兼容，尽量简洁，架构明确。更新文档一致性。最后 push（需人工确认）。
```

### 7.3 调试

```
/debugging
【bug 现象】。走红循环 → 最小复现 → 假设 → 插桩 → 修复 → 回归测试。找根因，不贴补丁。
```

### 7.4 安全审查

```
/security-review
审查本次改动：密钥、鉴权、注入、访问控制、加固。输出安全发现报告。
```

## 09 · operate — 运行与维护

**技能**：`documentation-audit` / `observability` / `handoff`

### 9.1 文档同步

```
/documentation-audit
根据当前代码同步所有文档：prd/tech/todo/api/flow 五类保持一致。
不需要审计报告，确保明确性和一致性，语言干练简洁，成熟风格。
```

### 9.2 可观测性

```
/observability
为系统加日志/指标/告警/插桩，让运行时行为可观测。输出插桩 + 上线前清单。

```
/handoff
把当前工作交接给下一个会话/agent：上下文、决策、下一步。输出交接简报。

## 跨阶段产物提示词

### A. 业务流程文档 docs/FLOW/*.md

针对系统每个业务流程写一份文档，含 mermaid 图 + 详细数据流描述。

```
针对每个业务数据流，结合已有图表创建 mermaid 图（简洁，体现架构即可），每个图配详细文字描述。
然后按业务划分、针对后端详细 API 端点，描述从输入到输出的完整数据流，必须体现分层架构
（接入层/业务层/数据层），明确每步调用的具体函数名（含类/模块前缀）。
格式：
  输入：<原始输入数据描述>
  1. 经由 <函数全名A> 处理，产出 <中间结果A描述>
  2. 经由 <函数全名B> 处理，产出 <中间结果B描述>
  输出：<最终输出数据描述>
约束：每步写出实际函数名；分层架构在步骤中自然体现；分支/异步按主路径描述并注明关键分支；
避免抽象概括，细化到每个有业务意义的函数调用。
```

### B. 前端审计 docs/FRONT.md

```
阅读整个前端项目，输出 docs/FRONT.md，明确每个步骤调用的具体组件名对应文件：
1. 目录结构 → 对应访问路由
2. server/client 组件划分
3. API 接口数据流向
4. 全局布局 & 公共组件复用
5. 启动命令与依赖配置
约束：清晰简洁越详细越好；每步写出实际函数名；分层架构自然体现；分支按主路径描述并注明。
```

### C. TODO 文档 docs/TODO.md

```
/code-review
深度检索前后端代码，每个代码文件都要查看。待优化处加 TODO 注释，已完成的删除。
输出 docs/TODO.md：按业务合并，成熟风格，全量 TODO 注释一致性审计（代码 ↔ TODO.md 双向校验），
更新相关文档确保一致性。
```

### D. CLAUDE.md 生成提示词

```
你是一位精通 {项目技术栈} 的资深开发者。
请为当前项目生成一份 CLAUDE.md，作为 AI 助手的上下文指令。根据 PRD/TECH 等文档生成。

## 结构要求（必须包含以下章节，顺序可微调）
1. 角色声明：AI 在本项目中的身份（如：你是一名 {React + Node.js} 全栈开发者…）
2. 关键前置操作：若依赖某些 Skill/工具/脚本，明确"在做相关操作前必须先加载/运行"
3. 项目概览：用途、核心目标、技术栈（语言/框架/数据库/运行时）
4. 常用命令：bash 代码块列出开发/构建/测试/启动/Lint 命令
5. 项目结构：表格列出关键目录和文件及职责
6. 开发边界：始终要做 / 绝不要做
7. 注释规范：语言、风格、示例
8. 资源：文档链接、技能列表、环境变量模板

## 内容约束（必须严格遵守）
- 纯净原则（最高行为准则）：一切代码和文档像第一次写出来的一样——不打补丁抓根因、
  代码自解释、不留残留文件、部署一致。

- 体现项目实际技术栈，角色声明/命令/目录结构根据下方具体技术栈定制，不能用泛泛表述。
- 测试代码写在 test/ 目录下，禁止 mock 测试（需要真实测试数据）。
- 代码有待完善处显式加 TODO 注释。

### E. 开源上线文档重构

```
/documentation-audit
文档 docs/ 只保留：prd / tech / todo / api / flow 五类，其他合并或删除。
重构要求：
- prd、tech 以 mermaid 图为主，文字简洁，成熟风格。
